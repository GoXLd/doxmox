+     <div class="sect4">
+      <h5 id="pvesdn_wireguard_node">
+       On the Node
+       <a class="headerlink" href="#pvesdn_wireguard_node" title="Permalink to this heading">
+       </a>
+      </h5>
+      <div class="paragraph">
+       <p>
+        There are two types of nodes: internal and external. Internal nodes are Proxmox
+VE nodes, external nodes everything else. They are essentially reusable peer
+definitions that can be used across the whole cluster.
+       </p>
+      </div>
+      <div class="dlist">
+       <div class="title">
+        Internal
+       </div>
+       <dl>
+        <dt class="hdlist1">
+         Endpoint
+        </dt>
+        <dd>
+         <p>
+          This is the IP or hostname that other Proxmox VE nodes should use for
+connecting to this Proxmox VE node. This is used as the endpoint when
+configuring this Proxmox VE node as a peer.
+         </p>
+        </dd>
+        <dt class="hdlist1">
+         Allowed IPs
+        </dt>
+        <dd>
+         <p>
+          A comma-separated list of CIDRs (for example
+          <span class="monospaced">
+           198.51.100.0/24
+          </span>
+          ,
+or
+          <span class="monospaced">
+           0.0.0.0/0
+          </span>
+          to tunnel all IPv4 traffic). When selecting this node as a peer
+on other nodes, the list is used as the
+          <span class="monospaced">
+           AllowedIPs
+          </span>
+          setting in the WireGuard
+peer configuration, that is, both the source filter for incoming traffic and
+the routing destination for outgoing traffic to this node.
+         </p>
+        </dd>
+       </dl>
+      </div>

+       <div class="title">
+        External
+       </div>
+       <dl>
+        <dt class="hdlist1">
+         Name
+        </dt>
+        <dd>
+         <p>
+          The name of the external node.
+         </p>
+        </dd>
+        <dt class="hdlist1">
+         Public Key
+        </dt>
+        <dd>
+         <p>
+          The public key used by the external node.
+         </p>
+        </dd>
+        <dt class="hdlist1">
+         Endpoint
+        </dt>

+         <p>

+         </p>
+        </dd>
+        <dt class="hdlist1">

+          </span>

+       <a class="headerlink" href="#pvesdn_wireguard_interface" title="Permalink to this heading">
+       </a>

+      <div class="dlist">
+       <dl>
+        <dt class="hdlist1">
+         Name
+        </dt>
+        <dd>
+         <p>
+          The name of the network interface on the Linux host. One to eight
+characters that must start with an alphanumeric character; the remaining
+characters may be alphanumeric or hyphens.
+         </p>
+        </dd>
+        <dt class="hdlist1">
+         IP
+        </dt>
+        <dd>
+         <p>
+          The IPv4 address in CIDR notation that should be configured on this
+interface (for example
+          <span class="monospaced">
+           198.51.100.1/24
+          </span>
+          ).
+         </p>
+        </dd>
+        <dt class="hdlist1">
+         IPv6
+        </dt>
+        <dd>
+         <p>
+          The IPv6 address in CIDR notation that should be configured on this
+interface (for example
+          <span class="monospaced">
+           2001:db8::1/64
+          </span>
+          ).
+         </p>
+        </dd>
+        <dt class="hdlist1">
+         Listen Port
+        </dt>
+        <dd>
+         <p>
+          The listening port for this interface.
+         </p>
+        </dd>
+        <dt class="hdlist1">
+         Peers
+        </dt>
+        <dd>
+         <p>
+          A list of peers that should be configured for that interface. All nodes
+that are part of the fabric can be selected as peers - the peer definition will
+be auto-generated from the configuration in the node.
+         </p>
+        </dd>
+       </dl>
+      </div>
+      <div class="paragraph">
+       <p>
+        When defining an interface, Proxmox VE automatically generates a private key
+for it in
+        <span class="monospaced">
+         /etc/pve/priv/wg-keys.cfg
+        </span>
+        upon saving the interface, and stores the
+matching public key alongside the interface in the fabric configuration so it
+can be shown in the Web UI when editing the node. Removing an interface from a
+node removes the corresponding private key from
+        <span class="monospaced">
+         wg-keys.cfg
+        </span>
+        as part of the
+same API call.
+       </p>
+      </div>
+      <div class="paragraph">
+       <p>
+        The fabric automatically generates routes through the WireGuard interface for
+every peer’s allowed IPs. For example, if interface wg0 has two peers with
+        <span class="monospaced">
+         198.51.100.0/24
+        </span>
+        and
+        <span class="monospaced">
+         203.0.113.0/24
+        </span>
+        as allowed IPs, then routes for both
+subnets are created. If the peer references the interface of a Proxmox VE node,
+that interface’s configured IP address is additionally added as a host route to
+the allowed IPs (for example, a peer node configured with
+        <span class="monospaced">
+         192.0.2.10/24
+        </span>
+        gets
+        <span class="monospaced">
+         192.0.2.10/32
+        </span>
+        added).

+   <div class="sect2">
+    <h3 id="pvesdn_config_route_filtering">
+     <span>
+      12.11. Prefix Lists and Route Maps
+     </span>
+     <a class="headerlink" href="#pvesdn_config_route_filtering" title="Permalink to this heading">
+     </a>
+    </h3>
+    <div class="paragraph">
+     <p>
+      Prefix lists and route maps let you control which routes are exchanged between
+the Proxmox VE nodes and their BGP, EVPN, OSPF, or OpenFabric peers, and modify
+attributes of those routes on the way in or out. The two work together: a
+prefix list classifies routes by their destination CIDR, while a route map
+chains match conditions and actions into an ordered policy.
+     </p>
+    </div>
+    <div class="paragraph">
+     <p>
+      If you have used
+      <span class="monospaced">
+       ip prefix-list
+      </span>
+      and
+      <span class="monospaced">
+       route-map
+      </span>
+      on FRR, Cisco IOS, or Juniper
+before, the Proxmox VE entities behave the same way. The Proxmox VE layer manages the
+configuration as cluster-wide entities under
+      <span class="monospaced">
+       /etc/pve/sdn/
+      </span>
+      and translates them
+to FRR
+      <span class="monospaced">
+       prefix-list
+      </span>
+      and
+      <span class="monospaced">
+       route-map
+      </span>
+      stanzas when applying the SDN
+configuration. The merged FRR configuration ends up in
+      <span class="monospaced">
+       /etc/frr/frr.conf
+      </span>
+      on
+each node; any node-local additions in
+      <span class="monospaced">
+       /etc/frr/frr.conf.local
+      </span>
+      are appended
+on top.
+     </p>
+    </div>
+    <div class="paragraph">
+     <p>
+      Like the rest of the SDN configuration, edits go to a pending state first and
+become active only after you apply changes in the main
+      <span class="monospaced">
+       SDN
+      </span>
+      panel.
+     </p>
+    </div>
+    <div class="sect3">
+     <h4 id="pvesdn_config_prefix_lists">
+      12.11.1. Prefix Lists
+      <a class="headerlink" href="#pvesdn_config_prefix_lists" title="Permalink to this heading">
+      </a>
+     </h4>
+     <div class="paragraph">
+      <p>
+       A prefix list is an ordered, named list of entries that each match a single
+destination CIDR (or a range of prefix lengths within that CIDR) and either
+       <span class="monospaced">
+        permit
+       </span>
+       or
+       <span class="monospaced">
+        deny
+       </span>
+       it. FRR evaluates entries in order of their sequence number
+and stops at the first match; if no entry matches, the prefix list denies
+implicitly, same as plain FRR.
+      </p>
+     </div>
+     <div class="paragraph">
+      <p>
+       Prefix lists are managed under
+       <span class="monospaced">
+        Datacenter -&gt; SDN -&gt; Prefix Lists
+       </span>
+       . Each list
+has a name and contains one or more entries with the following properties:
+      </p>
+     </div>
+     <div class="dlist">
+      <dl>
+       <dt class="hdlist1">
+        Sequence Nr.
+       </dt>
+       <dd>
+        <p>
+         Order in which the entry is evaluated within the list. Must be
+unique per list and at least
+         <span class="monospaced">
+          1
+         </span>
+         . If left empty on creation, Proxmox VE auto-assigns
+the next free sequence number using the convention
+         <span class="monospaced">
+          max + 5
+         </span>
+         , leaving room for
+later insertions.
+        </p>
+       </dd>
+       <dt class="hdlist1">
+        Action
+       </dt>
+       <dd>
+        <p>
+         Either
+         <span class="monospaced">
+          permit
+         </span>
+         or
+         <span class="monospaced">
+          deny
+         </span>
+         . There is an implicit
+         <span class="monospaced">
+          deny
+         </span>
+         at the end of
+each list.
+        </p>
+       </dd>
+       <dt class="hdlist1">
+        Prefix
+       </dt>
+       <dd>
+        <p>
+         Destination network in CIDR notation, for example
+         <span class="monospaced">
+          192.0.2.0/24
+         </span>
+         or
+         <span class="monospaced">
+          2001:db8::/32
+         </span>
+         . The prefix
+         <span class="monospaced">
+          0.0.0.0/0
+         </span>
+         (and
+         <span class="monospaced">
+          ::/0
+         </span>
+         ) is allowed and matches the
+default route.
+        </p>
+       </dd>
+       <dt class="hdlist1">
+        Prefix &gt;= (
+        <span class="monospaced">
+         ge
+        </span>
+        )
+       </dt>
+       <dd>
+        <p>
+         Optional minimum prefix length. If set, the entry matches
+any subnet of
+         <span class="monospaced">
+          prefix
+         </span>
+         whose length is at least
+         <span class="monospaced">
+          ge
+         </span>
+         .
+        </p>
+       </dd>
+       <dt class="hdlist1">
+        Prefix ⇐ (
+        <span class="monospaced">
+         le
+        </span>
+        )
+       </dt>
+       <dd>
+        <p>
+         Optional maximum prefix length. If set, the entry matches
+any subnet of
+         <span class="monospaced">
+          prefix
+         </span>
+         whose length is at most
+         <span class="monospaced">
+          le
+         </span>
+         .
+        </p>
+       </dd>
+      </dl>
+     </div>
+     <div class="paragraph">
+      <p>
+       Without
+       <span class="monospaced">
+        le
+       </span>
+       or
+       <span class="monospaced">
+        ge
+       </span>
+       an entry matches the prefix exactly. With both set, it
+matches any subnet within the given length range. For example
+       <span class="monospaced">
+        10.0.0.0/8 ge 16 le 24
+       </span>
+       matches every /16 to /24 subnet inside
+       <span class="monospaced">
+        10.0.0.0/8
+       </span>
+       .
+This is the standard FRR/Cisco semantics. Additional validation enforced by
+Proxmox VE:
+       <span class="monospaced">
+        ge
+       </span>
+       must not exceed
+       <span class="monospaced">
+        le
+       </span>
+       , neither may be smaller than the prefix’s own
+length, and both must stay within the address family bound (/32 for IPv4,
+/128 for IPv6).
+      </p>

+    <div class="sect3">
+     <h4 id="pvesdn_config_route_maps">
+      12.11.2. Route Maps
+      <a class="headerlink" href="#pvesdn_config_route_maps" title="Permalink to this heading">
+      </a>
+     </h4>
+     <div class="paragraph">
+      <p>
+       A route map is an ordered list of entries that match incoming or outgoing
+routes against criteria, optionally modify attributes such as the metric or
+local preference, and either
+       <span class="monospaced">
+        permit
+       </span>
+       (forward the route, possibly modified) or
+       <span class="monospaced">
+        deny
+       </span>
+       (drop the route). FRR evaluates entries in order; the first match
+controls the action. Every route map implicitly has an otherwise empty
+       <span class="monospaced">
+        deny
+       </span>
+       as
+its last entry, denying all routes that did not match an entry explicitly.
+      </p>
+     </div>
+     <div class="paragraph">
+      <p>
+       Route maps are managed under
+       <span class="monospaced">
+        Datacenter -&gt; SDN -&gt; Route Maps
+       </span>
+       . Each entry has
+the following properties:
+      </p>
+     </div>
+     <div class="dlist">
+      <dl>
+       <dt class="hdlist1">
+        Order
+       </dt>
+       <dd>
+        <p>
+         Order in which the entry is evaluated, between
+         <span class="monospaced">
+          0
+         </span>
+         and
+         <span class="monospaced">
+          65535
+         </span>
+         .
+Mandatory and must be unique within a route map. Leaving gaps between orders,
+for example assigning entries
+         <span class="monospaced">
+          10
+         </span>
+         ,
+         <span class="monospaced">
+          20
+         </span>
+         ,
+         <span class="monospaced">
+          30
+         </span>
+         , leaves room for later
+insertions without renumbering.
+        </p>
+       </dd>
+       <dt class="hdlist1">
+        Action
+       </dt>
+       <dd>
+        <p>
+         Either
+         <span class="monospaced">
+          permit
+         </span>
+         or
+         <span class="monospaced">
+          deny
+         </span>
+         .
+         <span class="monospaced">
+          permit
+         </span>
+         lets the route pass (after any
+         <span class="monospaced">
+          set
+         </span>
+         actions);
+         <span class="monospaced">
+          deny
+         </span>
+         drops it.
+        </p>
+       </dd>
+       <dt class="hdlist1">
+        Match
+       </dt>
+       <dd>
+        <p>
+         One or more match conditions. Available keys are:
+         <span class="monospaced">
+          route-type
+         </span>
+         ,
+         <span class="monospaced">
+          vni
+         </span>
+         ,
+         <span class="monospaced">
+          ip-address-prefix-list
+         </span>
+         ,
+         <span class="monospaced">
+          ip6-address-prefix-list
+         </span>
+         ,
+         <span class="monospaced">
+          ip-next-hop-prefix-list
+         </span>
+         ,
+         <span class="monospaced">
+          ip6-next-hop-prefix-list
+         </span>
+         ,
+         <span class="monospaced">
+          ip-next-hop-address
+         </span>
+         ,
+         <span class="monospaced">
+          ip6-next-hop-address
+         </span>
+         ,
+         <span class="monospaced">
+          metric
+         </span>
+         ,
+         <span class="monospaced">
+          local-preference
+         </span>
+         , and
+         <span class="monospaced">
+          peer
+         </span>
+         . The four
+         <span class="monospaced">
+          *-prefix-list
+         </span>
+         keys
+reference a prefix list by name. All match conditions of an entry must be true
+for it to apply.
+        </p>
+       </dd>
+       <dt class="hdlist1">
+        Set
+       </dt>
+       <dd>
+        <p>
+         One or more attributes to set when the entry matches. Available keys are
+         <span class="monospaced">
+          ip-next-hop
+         </span>
+         ,
+         <span class="monospaced">
+          ip-next-hop-peer-address
+         </span>
+         ,
+         <span class="monospaced">
+          ip-next-hop-unchanged
+         </span>
+         ,
+         <span class="monospaced">
+          ip6-next-hop
+         </span>
+         ,
+         <span class="monospaced">
+          ip6-next-hop-peer-address
+         </span>
+         ,
+         <span class="monospaced">
+          ip6-next-hop-prefer-global
+         </span>
+         ,
+         <span class="monospaced">
+          local-preference
+         </span>
+         ,
+         <span class="monospaced">
+          tag
+         </span>
+         ,
+         <span class="monospaced">
+          weight
+         </span>
+         ,
+         <span class="monospaced">
+          metric
+         </span>
+         , and
+         <span class="monospaced">
+          src
+         </span>
+         . The
+         <span class="monospaced">
+          metric
+         </span>
+         value
+supports
+         <span class="monospaced">
+          N
+         </span>
+         ,
+         <span class="monospaced">
+          +N
+         </span>
+         ,
+         <span class="monospaced">
+          -N
+         </span>
+         (adjust),
+         <span class="monospaced">
+          rtt
+         </span>
+         ,
+         <span class="monospaced">
+          +rtt
+         </span>
+         ,
+         <span class="monospaced">
+          -rtt
+         </span>
+         ,
+         <span class="monospaced">
+          igp
+         </span>
+         , and
+         <span class="monospaced">
+          aigp
+         </span>
+         .
+The
+         <span class="monospaced">
+          tag
+         </span>
+         value accepts an integer or the literal
+         <span class="monospaced">
+          untagged
+         </span>
+         .
+        </p>
+       </dd>
+       <dt class="hdlist1">
+        Exit Action
+       </dt>
+       <dd>
+        <p>
+         Controls how evaluation continues after a match. Leave empty for
+the default behavior (terminate on match).
+         <span class="monospaced">
+          on-match-next
+         </span>
+         proceeds with the
+immediately following entry.
+         <span class="monospaced">
+          on-match-goto &lt;order&gt;
+         </span>
+         jumps to the first entry
+whose order is greater than or equal to the given value.
+         <span class="monospaced">
+          continue &lt;order&gt;
+         </span>
+         jumps to the entry with exactly that order. All three correspond to the FRR
+         <span class="monospaced">
+          on-match
+         </span>
+         /
+         <span class="monospaced">
+          continue
+         </span>
+         directives.
+        </p>
+       </dd>
+       <dt class="hdlist1">
+        Call
+       </dt>
+       <dd>
+        <p>
+         Optionally call another route map at the end of this entry’s processing.
+This corresponds to the FRR
+         <span class="monospaced">
+          call
+         </span>
+         directive.
+        </p>
+       </dd>
+      </dl>
+     </div>

-    <div class="sect3">
-     <h4 id="_crs_scheduling_points">
-      15.13.3. CRS Scheduling Points
-      <a class="headerlink" href="#_crs_scheduling_points" title="Permalink to this heading">
-      </a>
-     </h4>
      <div class="paragraph">
       <p>
-       The CRS algorithm is not applied for every service in every round, since this
-would mean a large number of constant migrations. Depending on the workload,
-this could put more strain on the cluster than could be avoided by constant
-balancing.
-That’s why the Proxmox VE HA manager favors keeping services on their current node.
+       The automatic load balancing system can be enabled and configured in the web
+interface under
+       <span class="monospaced">
+        Datacenter
+       </span>
+       →
+       <span class="monospaced">
+        Options
+       </span>
+       →
+       <span class="monospaced">
+        Cluster Resource Scheduling
+       </span>
+       .
+This allows fine-tuning the various parameters as described in the next
+paragraph for different cluster setups and requirements. The load balancer
+requires either the
+       <a href="#ha_manager_crs_static_scheduler">
+        static-load
+       </a>
+       or
+       <a href="#ha_manager_crs_dynamic_scheduler">
+        dynamic-load
+       </a>
+       scheduler mode to be in use.
       </p>
      </div>
      <div class="paragraph">
       <p>
-       The CRS is currently used at the following scheduling points:
+       In every HA Manager round, each of which lasts around 10 seconds, the
+automatic load balancer checks whether the cluster imbalance exceeds the
+       <em>
+        imbalance threshold
+       </em>
+       . If the cluster imbalance stays above the threshold for
+at least as many consecutive HA Manager rounds as the
+       <em>
+        hold duration
+       </em>
+       , then
+the load balancer will select the rebalancing migration for an HA resource,
+which lowers the overall cluster imbalance the most. The method used to select
+the best rebalancing migration can be set with the
+       <em>
+        rebalancing method
+       </em>
+       option. Finally, if the selected migration reduces the current cluster
+imbalance by at least the percentage given by the
+       <em>
+        imbalance improvement
+       </em>
+       option, the load balancer issues the selected migration.
       </p>
      </div>
-     <div class="ulist">
-      <ul>
-       <li>
-        <p>
-         Service recovery (always active). When a node with active HA services fails,
-  all its services need to be recovered to other nodes. The CRS algorithm will
-  be used here to balance that recovery over the remaining nodes.
-        </p>
-       </li>
-       <li>
-        <p>
-         HA group config changes (always active). If a node is removed from a group,
-  or its priority is reduced, the HA stack will use the CRS algorithm to find a
-  new target node for the HA services in that group, matching the adapted
-  priority constraints.
-        </p>
-       </li>
-       <li>
-        <p>
-         HA rule config changes (always active). If a rule emposes different
-  constraints on the HA resources, the HA stack will use the CRS algorithm to
-  find a new target node for the HA resources affected by these rules depending
-  on the type of the new rules:
-        </p>
-        <div class="ulist">
-         <ul>
-          <li>
-           <p>
-            Node affinity rules: If a node affinity rule is created or HA resources/nodes
-   are added to an existing node affinity rule, the HA stack will use the CRS
-   algorithm to ensure that these HA resources are assigned according to their
-   node and priority constraints.
-           </p>
-          </li>
-          <li>
-           <p>
-            Positive resource affinity rules: If a positive resource affinity rule is
-   created or HA resources are added to an existing positive resource affinity
-   rule, the HA stack will use the CRS algorithm to ensure that these HA
-   resources are moved to a common node.
-           </p>
-          </li>
-          <li>
-           <p>
-            Negative resource affinity rules: If a negative resource affinity rule is
-   created or HA resources are added to an existing negative resource affinity
-   rule, the HA stack will use the CRS algorithm to ensure that these HA
-   resources are moved to separate nodes.
-           </p>
-          </li>
-         </ul>
-        </div>
-       </li>
-       <li>
-        <p>
-         HA service stopped → start transition (opt-in). Requesting that a stopped
-  service should be started is an good opportunity to check for the best suited
-  node as per the CRS algorithm, as moving stopped services is  cheaper to do
-  than moving them started, especially if their disk volumes reside on shared
-  storage. You can enable this by setting the
-         <strong>
-          <span class="monospaced">
-           ha-rebalance-on-start
-          </span>
-         </strong>
-         CRS option in the datacenter config. You can change that option also in the
-  Web UI, under
-         <span class="monospaced">
-          Datacenter
-         </span>
-         →
-         <span class="monospaced">
-          Options
-         </span>
-         →
-         <span class="monospaced">
-          Cluster Resource Scheduling
-         </span>
-         .
-        </p>
-       </li>
-      </ul>
+     <div class="paragraph">
+      <p>
+       The cluster imbalance is calculated as the ratio between the standard deviation
+and mean of the individual node loads. Therefore, the
+       <em>
+        imbalance threshold
+       </em>
+       controls the sensitivity of the load balancer. If the
+       <em>
+        imbalance threshold
+       </em>
+       is
+set to a value of
+       <span class="monospaced">
+        0.0
+       </span>
+       , it will try to select a rebalancing migration every
+time the
+       <em>
+        hold duration
+       </em>
+       is exceeded. The
+       <em>
+        imbalance improvement
+       </em>
+       percentage
+filters what constitutes an acceptable rebalancing migration. If it is set to
+       <span class="monospaced">
+        0.0
+       </span>
+       , then it will always commit to a migration even if the expected
+imbalance does not change at all. However, the value can never be negative, so
+it will never commit to a migration with an expected imbalance worse than the
+current one.
+      </p>
