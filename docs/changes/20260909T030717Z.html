+    <div class="sect3">
+     <h4 id="pveceph_cephx_migration">
+      8.14.5. Migrate Cephx Keys from
+      <span class="monospaced">
+       aes
+      </span>
+      to
+      <span class="monospaced">
+       aes256k
+      </span>
+      <a class="headerlink" href="#pveceph_cephx_migration" title="Permalink to this heading">
+      </a>
+     </h4>
+     <div class="paragraph">
+      <p>
+       This section explains how to migrate the cluster-owned keys and the keys of
+compatible Ceph users from
+       <span class="monospaced">
+        aes
+       </span>
+       to
+       <span class="monospaced">
+        aes256k
+       </span>
+       . For an explanation of Ceph
+users, tickets, and key storage, see
+       <a href="#pveceph_cephx_how_it_works">
+        Cephx Authentication
+       </a>
+       .
+      </p>
+     </div>
+     <div class="sect4">
+      <h5 id="_why_the_health_checks_appear">
+       Why the Health Checks Appear
+       <a class="headerlink" href="#_why_the_health_checks_appear" title="Permalink to this heading">
+       </a>
+      </h5>
+      <div class="paragraph">
+       <p>
+        Ceph Squid 19.2.6 and Ceph Tentacle 20.2.4 add health checks for keys and
+temporary access credentials that use the older
+        <span class="monospaced">
+         aes
+        </span>
+        encryption method. The
+checks can therefore appear directly after an upgrade even if the cluster
+worked without warnings before. The older method is affected by
+        <a href="https://docs.ceph.com/en/latest/security/CVE-2025-30156">
+         <em>
+          CVE-2025-30156
+         </em>
+        </a>
+        .
+See the upstream release announcement for background
+        <span class="footnote">
+         <br/>
+         [Ceph: Squid
+v19.2.6 and Tentacle v20.2.4 released
+         <a href="https://ceph.io/en/news/blog/2026/v20-2-4-v19-2-6-combo-released/">
+          https://ceph.io/en/news/blog/2026/v20-2-4-v19-2-6-combo-released/
+         </a>
+         ]
+         <br/>
+        </span>
+        .
+       </p>
+      </div>
+      <div class="paragraph">
+       <p>
+        Two checks set the cluster status to
+        <em>
+         HEALTH_ERR
+        </em>
+        . This does not mean that
+storage access or a Ceph service has failed. Follow the steps below to migrate
+to
+        <span class="monospaced">
+         aes256k
+        </span>
+        and, when all clients support it, disable the vulnerable method.
+       </p>
+      </div>
+     </div>
+     <div class="sect4">
+      <h5 id="pveceph_cephx_migration_helper">
+       Migration Steps
+       <a class="headerlink" href="#pveceph_cephx_migration_helper" title="Permalink to this heading">
+       </a>
+      </h5>
+      <div class="paragraph">
+       <p>
+        The migration helper checks the cluster, rotates keys, and resumes interrupted
+work. Review each dry run before applying its plan; add
+        <span class="monospaced">
+         --verbose
+        </span>
+        for full
+node, keyring, and device inventories.
+       </p>
+      </div>
+      <div class="paragraph">
+       <p>
+        Reruns do not rotate completed keys again. After each run, invoke the helper
+without options to check the current state and follow the next steps it prints.
+       </p>
+      </div>
+      <div class="ulist">
+       <div class="title">
+        Before You Begin
+       </div>
+       <ul>
+        <li>
+         <p>
+          Upgrade
+          <span class="monospaced">
+           pve-manager
+          </span>
+          to 9.2.17 or newer and install the latest Ceph
+  packages on every node. Staged client-key rotation requires Ceph
+  19.2.6-pve3, 20.2.4-pve3, or newer on every monitor. Then complete the
+  rolling restart of all Ceph services.
+         </p>
+        </li>
+        <li>
+         <p>
+          Resolve health warnings and errors not listed in
+          <a href="#pveceph_cephx_health_check_reference">
+           Health Check Reference
+          </a>
+          . Ensure
+  every node is reachable over SSH.
+         </p>
+        </li>
+        <li>
+         <p>
+          Run the helper as
+          <span class="monospaced">
+           root
+          </span>
+          on one node only. Do not start another migration,
+  a rolling restart, or change Ceph keys with other tools while it runs. The
+  helper’s lock does not block direct Ceph authentication commands.
+         </p>
+        </li>
+       </ul>
+      </div>

+       <div class="paragraph">
+        <p>
+         Review the cluster-owned migration in the default dry-run mode:
+        </p>

+        </div>
+       </div>
+       <div class="paragraph">
+        <p>
+         If the plan reports no blocker, apply the same selection:
+        </p>
+       </div>

+        <div class="content">
+         <!-- Generator: GNU source-highlight
+by Lorenzo Bettini
+http://www.lorenzobettini.it
+http://www.gnu.org/software/src-highlite -->
+         <pre><tt>/usr/share/pve-manager/migrations/pve-cephx-rotate-service-keys --rotate-cluster-keys --apply</tt></pre>
+        </div>
+       </div>
+       <div class="paragraph">
+        <p>
+         The helper rotates the manager, metadata server, OSD, monitor, bootstrap, crash,

+         <a href="#pveceph_cephx_lockbox">
+          encrypted OSD lockbox keys

+         . It restarts services

+        <p>
+         After Ceph updates its health status, the two error-severity checks clear. The
+warning about rotating service keys can remain for a few hours and clears

+        </p>

+      <div class="sect5">
+       <h6 id="pveceph_cephx_migration_clients">
+        2. Migrate the Keys of Compatible Ceph Users
+        <a class="headerlink" href="#pveceph_cephx_migration_clients" title="Permalink to this heading">
+        </a>
+       </h6>
+       <div class="paragraph" id="pveceph_cipher_support">
+        <div class="title">
+         Check compatibility
+        </div>
+        <p>
+         Several workloads can share one Ceph user. Migrate its key only when every
+client supports
+         <span class="monospaced">
+          aes256k
+         </span>
+         , including disconnected and external clients.

+require a
+         <strong>
+          running
+         </strong>
+         kernel version 7.0 or newer.

+         </a>
+        </p>

+            </p>

+        </table>
+       </div>
+       <div class="paragraph">
+        <p>
+         Check external systems too. If any affected client is incompatible or
+unknown, leave its user’s key unchanged and postpone this step.
+        </p>
+       </div>

+        <div class="title">
+         Stage the keys
+        </div>
+        <p>
+         Use
+         <span class="monospaced">
+          --rotate-all-storage-keys
+         </span>

+         <span class="monospaced">
+          --rotate-admin-key
+         </span>
+         for
+         <span class="monospaced">
+          client.admin
+         </span>
+         ,
+which the command line and storages without their own user share. Every
+client of these users is affected; storages of external clusters are
+excluded.
+        </p>
+       </div>

+        <p>
+         The helper stages each new key and writes it to the managed keyring and secret
+files. Both keys remain valid until confirmation, allowing clients to refresh
+before the old key is retired. If a monitor cannot keep both keys valid, the
+helper refuses staging and names the monitor to update or restart.
+        </p>
+       </div>

+        <p>
+         Review the combined plan:
+        </p>
+       </div>

+    --rotate-all-storage-keys --rotate-admin-key --apply</tt></pre>
+        </div>
+       </div>
+       <div class="paragraph">
+        <p>
+         While a key is staged, do not add or downgrade monitors or change that user’s
+keys with other tools. Its
+         <span class="monospaced">
+          AUTH_INSECURE_CLIENT_KEY_TYPE
+         </span>
+         warning remains
+until confirmation makes the new key current and invalidates the old one.
+        </p>
+       </div>
+       <div class="ulist" id="pveceph_cephx_refresh_clients">
+        <div class="title">
+         Refresh Clients
+        </div>
+        <ul>
+         <li>
+          <p>
+           Live-migrate affected virtual machines in the web interface, or stop and
+  start them. A guest reboot is not enough.
+          </p>
+         </li>
+         <li>
+          <p>
+           Stop and start affected containers and other RBD clients.
+          </p>
+         </li>
+         <li>
+          <p>
+           Let backups, restores, disk imports, and clones on Ceph storage finish
+  before confirmation; these operations can retain the key they started with.
+          </p>
+         </li>
+         <li>
+          <p>
+           The helper refreshes idle CephFS mounts and leaves busy or unresponsive
+  mounts alone. Once nothing uses them, rerun the helper with
+           <span class="monospaced">
+            --apply
+           </span>
+           to
+  retry the outstanding mounts.
+          </p>
+         </li>
+         <li>
+          <p>
+           For clients outside Proxmox VE, distribute the staged credential from the
+           <a href="#pveceph_cephx_external_copies">
+            managed key files
+           </a>
+           , then restart or remount
+  those clients.
+          </p>
+         </li>
+        </ul>
+       </div>

+         The helper reports sessions that may still hold an old key. Client names

+and external key copies yourself.

+       <h6 id="pveceph_cephx_staged_keys">
+        Staged Keys and Confirmation
+        <a class="headerlink" href="#pveceph_cephx_staged_keys" title="Permalink to this heading">
+        </a>
+       </h6>
+       <div class="paragraph">
+        <p>
+         The helper disables automatic promotion of pending client keys so that the
+monitors keep both credentials valid. An older monitor would promote a staged
+key on its first use and end the grace period for the whole cluster. The
+helper therefore stages only when every monitor supports the feature and
+checks this again on every run.
+        </p>
+       </div>
+       <div class="paragraph">
+        <p>
+         With
+         <span class="monospaced">
+          --apply
+         </span>
+         ,
+         <span class="monospaced">
+          --confirm-all-clients-refreshed
+         </span>
+         makes every staged key current
+and invalidates its previous key. The initial check refuses the entire batch
+if any open rotation is not ready. The helper then rechecks each key before
+retiring its old credential. If a client returns during the batch, completed
+rotations stay committed and the blocked key stays staged. To confirm ready
+users separately, use
+         <span class="monospaced">
+          --confirm-clients-refreshed &lt;USER&gt;
+         </span>
+         with
+         <span class="monospaced">
+          --apply
+         </span>
+         .
+        </p>
+       </div>
+      </div>
+      <div class="sect5">
+       <h6 id="pveceph_cephx_external_copies">
+        Key Copies for External Clients
+        <a class="headerlink" href="#pveceph_cephx_external_copies" title="Permalink to this heading">
+        </a>
+       </h6>
+       <div class="paragraph">
+        <p>
+         For an external client of the local cluster, copy the staged credential from
+the managed file for its Ceph user:
+        </p>
+       </div>
+       <div class="ulist">
+        <ul>
+         <li>
+          <p>
+           RBD keyring:
+           <span class="monospaced">
+            /etc/pve/priv/ceph/&lt;STORAGE_ID&gt;.keyring
+           </span>
+          </p>
+         </li>
+         <li>
+          <p>
+           CephFS bare secret:
+           <span class="monospaced">
+            /etc/pve/priv/ceph/&lt;STORAGE_ID&gt;.secret
+           </span>
+          </p>
+         </li>
+         <li>
+          <p>
+           Administrative keyring:
+           <span class="monospaced">
+            /etc/pve/priv/ceph.client.admin.keyring
+           </span>
+          </p>
+         </li>
+        </ul>
+       </div>
+       <div class="paragraph">
+        <p>
+         Use the credential for that user, not
+         <span class="monospaced">
+          client.admin
+         </span>
+         as a substitute. Transfer
+it securely and update every saved copy before refreshing the client.
+Storage backed by an external cluster is different: the helper never rotates
+that cluster’s keys. Follow its administrator’s key-rotation procedure.
+        </p>
+       </div>
+       <div class="paragraph">
+        <p>
+         The helper lists local users not managed by Proxmox VE separately. Follow their
+client’s supported rotation procedure, or leave their keys unchanged and keep
+the old cipher enabled.
+        </p>

+       <h6 id="pveceph_cephx_rollback">
+        Roll Back a Staged Client Key
+        <a class="headerlink" href="#pveceph_cephx_rollback" title="Permalink to this heading">
+        </a>
+       </h6>
+       <div class="paragraph">
+        <p>
+         To return a staged user to its current key:
+        </p>
+       </div>
+       <div class="olist arabic">
+        <ol class="arabic">
+         <li>
+          <p>
+           Run the helper with
+           <span class="monospaced">
+            --abort-staged-key &lt;USER&gt; --apply
+           </span>
+           . It restores the
+  current key to every managed copy while both credentials remain valid.
+          </p>
+         </li>
+         <li>
+          <p>
+           Refresh all clients back to that key, including disconnected clients and
+  external key copies. The helper retries managed CephFS mounts as during
+  forward migration.
+          </p>
+         </li>
+         <li>
+          <p>
+           Run the helper with
+           <span class="monospaced">
+            --confirm-abort-clients-refreshed &lt;USER&gt; --apply
+           </span>
+           to
+  retire the staged key. The helper refuses if monitor session collection is
+  incomplete, a visible session uses the staged key, or its key is unknown.
+          </p>
+         </li>
+        </ol>
+       </div>
+       <div class="paragraph">
+        <p>
+         Ceph 19.2.6-pve4 and 20.2.4-pve4 or newer monitors can identify each session’s
+key, allowing clients on the restored key to stay connected during rollback
+confirmation. Upgrade and restart older monitors to use this feature. Without
+key identification, every visible client of that user must disconnect before
+confirmation; upgrading is preferable for a shared user such as
+         <span class="monospaced">
+          client.admin
+         </span>
+         .
+        </p>

+       <h6 id="_emergency_cipher_override">
+        Emergency Cipher Override
+        <a class="headerlink" href="#_emergency_cipher_override" title="Permalink to this heading">
+        </a>
+       </h6>
+       <div class="paragraph">
+        <p>
+         Monitors normally use the
+         <span class="monospaced">
+          auth_allowed_ciphers
+         </span>
+         list stored in the MonMap to
+decide which key ciphers may authenticate. The local startup option
+         <span class="monospaced">
+          mon_auth_emergency_allowed_ciphers
+         </span>
+         replaces that list for a monitor. It can
+temporarily allow the cipher of an existing administrative key after an
+incorrect restriction locked administrators out
+         <span class="footnote">
+          <br/>
+          [Ceph: Emergency
+Allowed Ciphers
+          <a href="https://docs.ceph.com/en/tentacle/rados/configuration/auth-config-ref/#emergency-allowed-ciphers">
+           https://docs.ceph.com/en/tentacle/rados/configuration/auth-config-ref/#emergency-allowed-ciphers
+          </a>
+          ]
+          <br/>
+         </span>
+         .
+        </p>
+       </div>
+       <div class="paragraph">
+        <p>
+         Ceph raises
+         <span class="monospaced">
+          AUTH_EMERGENCY_CIPHERS_SET
+         </span>
+         while this override is configured. The
+helper refuses the final restriction because changing the MonMap would not
+take effect. Use the override only to recover access, then repair the normal
+configuration, remove it from
+         <span class="monospaced">
+          /etc/pve/ceph.conf
+         </span>
+         , and restart every monitor
+before the final dry run.
+        </p>
+       </div>
